# Switch 1のウェイクアッププロトコル

日本語 | [English](wakeup-protocol.en.md)

Nintendo Switch 1をスリープ状態から復帰させるコントローラーは、通常のBR/EDRページ接続より先に専用の通信処理を行う。<br>
この通信処理では、接続先となるSwitchのBD_ADDRから算出したウェイクアップ用アクセスコードを使用する。<br>
フェーズ1ではウェイクアップコードを反復送信し、フェーズ2ではSwitchから接続情報を受信し、フェーズ3ではコントローラー自身のBD_ADDRを送信する。<br>
フェーズ2で取得したLT_ADDRとクロック情報を使用してACLリンクを開始すると、Switchがスリープ状態から復帰する。

## 用語

| 用語 | 意味 |
|---|---|
| LAP | BD_ADDRの下位3byteで構成される24bit値 |
| 同期ワード | BR/EDRアクセスコード内で使用される64bit値 |
| ウェイクアップ用アクセスコード | 標準アクセスコードの同期ワードの下位32bitを反転したアクセスコード |
| ウェイクアップコード | フェーズ1のペイロードで送信する4byte値 |

ウェイクアップ用アクセスコードとウェイクアップコードは同じものではない。<br>
前者はパケットの同期に使用する72bitのアクセスコードであり、後者はその下位32bitと同じ値を送信byte順に並べた4byteのペイロードデータである。

## BR/EDRアクセスコード

BR/EDRのアクセスコードは72bitで構成される。

| フィールド | 長さ |
|---|---:|
| プリアンブル | 4bit |
| 同期ワード | 64bit |
| トレーラー | 4bit |

同期ワードは接続先のLAPから算出する。<br>
BD_ADDRの上位3byteは計算に使用しないため、LAPが同じBD_ADDRからは同じ同期ワードが得られる。

```text
54:f7:08:90:34:25 -> LAP = 0x903425
ef:4a:c5:1a:00:ee -> LAP = 0x1A00EE
```

計算にはBluetooth仕様で定義されている次の値を使用する。

```text
PN        = 0x83848D96BBCC54FC
GENERATOR = 0x585713DA9
```

`GENERATOR`は、Bluetooth仕様のBCH符号生成多項式`0x37CD0EB67`に、GF(2)の多項式として`D + 1`を乗算した値である。

```text
GENERATOR = (0x37CD0EB67 << 1) XOR 0x37CD0EB67
```

同期ワード`S`は次の手順で算出する。<br>
加算と減算にはGF(2)上のXORを使用する。

1. LAPの最上位bitに応じて6bitのBarker系列を選択し、BCH符号化へ入力する30bit値`U`を求める。

   ```text
   LAP bit23 = 0: U = 0x2C000000 OR LAP
   LAP bit23 = 1: U = 0x13000000 OR LAP
   ```

2. `PN`の上位30bitをXORする。

   ```text
   X = U XOR (PN >> 34)
   ```

3. `X`を34bit左へシフトし、`GENERATOR`で除算した剰余`R`を下位34bitへ加算する。

   ```text
   Z = X << 34
   R = Z mod GENERATOR
   C = Z XOR R
   ```

4. 64bitの`PN`をXORして同期ワードを求める。

   ```text
   S = C XOR PN
   ```

プリアンブルとトレーラーは、同期ワードの送信順における両端のbitから決定する。

```text
S bit0  = 1: preamble = 1010
S bit0  = 0: preamble = 0101
S bit63 = 1: trailer  = 0101
S bit63 = 0: trailer  = 1010
```

## ウェイクアップ用アクセスコード

ウェイクアップ用アクセスコードでは、標準の同期ワード`S`の下位32bitを反転する。

```text
P34        = S AND 0x3FFFFFFFF
P34_wakeup = P34 XOR 0xFFFFFFFF
```

`P34`は同期ワードの下位34bitであり、`P34_wakeup`では下位32bitが反転し、上位2bitは変化しない。<br>
Bluetoothコントローラーへ`P34_wakeup`とLAPを設定すると、コントローラーがプリアンブルとトレーラーを含む72bitのウェイクアップ用アクセスコードを算出する。

## ウェイクアップコード

ウェイクアップコードは、同期ワード`S`の下位32bitを反転し、リトルエンディアンの4byteとして並べた値である。

```text
W = (NOT S) AND 0xFFFFFFFF
wakeup_code = little_endian(W)
```

フェーズ1のペイロードでは、`W`を右へ10bitローテートした32bit値をリトルエンディアンで反復する。

```text
phase1_word = rotate_right(W, 10)
phase1_payload = repeat(little_endian(phase1_word))
```

これらの計算結果の例は以下の通り。

| BD_ADDR | 32bit値`W` | ウェイクアップコードの4byte | 72bitのウェイクアップ用アクセスコード |
|---|---|---|---|
| `55:55:55:55:55:55` | `0x79F98210` | `10 82 F9 79` | `AB155555579F98210A` |
| `aa:aa:aa:aa:aa:aa` | `0xFAD69689` | `89 96 D6 FA` | `54EAAAAA9FAD696895` |
| `54:f7:08:90:34:25` | `0x0CB13E3F` | `3F 3E B1 0C` | `54E40D0940CB13E3F5` |
| `ef:4a:c5:1a:00:ee` | `0xAF3BC02D` | `2D C0 3B AF` | `AB06803B9AF3BC02D5` |

## ウェイクアップの手順

3フェーズでは同じウェイクアップ用アクセスコードを使用する。

| フェーズ | 送信元 | 内容 | 目的 |
|---|---|---|---|
| 1 | コントローラー | ウェイクアップコードの反復 | スリープ中のSwitchへ応答を要求する |
| 2 | Switch | LT_ADDR、SwitchのBD_ADDR、ネイティブクロックを含む17byte | ACLリンクの開始に必要な情報を通知する |
| 3 | コントローラー | コントローラー自身のBD_ADDRと6byteのゼロパディング | コントローラーのアドレスをSwitchへ通知する |

### フェーズ1

コントローラーは、ウェイクアップコードを反復した生のRFパケットを3.75ms間隔で送信する。<br>
また、互換コントローラーのRFキャプチャによる実測ではDH3またはDH5が使用され、ペイロードは白色化されていない。<br>
これは任意のRFパケット送信を擬似的にBluetoothパケットで再現するための処理と考えられる。

### フェーズ2

Switchは標準のアクセスコードとは異なるウェイクアップ用アクセスコードを使用して応答する。<br>
RFキャプチャによる実測では、応答は17byteのペイロードを持つDM1として送信される。

| 項目 | 内容 |
|---|---|
| アクセスコード | `P34_wakeup` |
| パケットタイプ | DM1 |
| パケットヘッダー | `0x298`、LT_ADDR=0、TYPE=3、FLOW=1、ARQN=0、SEQN=1 |
| ペイロード長 | 17byte |
| 白色化 | なし |
| 送信間隔 | 3.75ms |

ペイロードのうち、接続開始に使用するフィールドは次のとおりである。

| byte位置 | 内容 |
|---|---|
| 0 | 下位3bitがLT_ADDR |
| 1~6 | SwitchのBD_ADDRを下位byteから格納 |
| 7~12 | 本プロジェクトでは未使用 |
| 13~16 | Switchのネイティブクロック |

ネイティブクロックは次の式で復元する。

```text
packed_clock = payload[13]
             OR (payload[14] << 8)
             OR (payload[15] << 16)
             OR ((payload[16] AND 0x1F) << 24)

remote_clock = packed_clock >> 2
```

コントローラーは`remote_clock`と応答を受信したローカルクロックとの差を計算し、ACLリンクのクロックオフセットとして使用する。

### フェーズ3

コントローラーは、最後に受信したフェーズ2応答の634us後にフェーズ3を送信する。<br>
RFキャプチャによる実測では、フェーズ3は12byteのペイロードを持つDM1である。

| 項目 | 内容 |
|---|---|
| アクセスコード | `P34_wakeup` |
| パケットタイプ | DM1 |
| パケットヘッダー | `0x298`、LT_ADDR=0、TYPE=3、FLOW=1、ARQN=0、SEQN=1 |
| ペイロードヘッダー | `0x67`、長さ12、FLOW=1、LLID=3 |
| ペイロード | コントローラーのBD_ADDRを下位byteから6byte、その後に6byteのゼロパディング |
| 白色化 | なし |
| 送信時刻 | 最後のフェーズ2応答から634us後 |

フェーズ3を受信したSwitchは短い応答を返す。<br>
この応答はフェーズ3の受信を示すが、スリープ状態からの復帰には次のACLリンク開始処理が必要である。

### ACLリンクの開始

コントローラーは、フェーズ2で取得したLT_ADDR、SwitchのBD_ADDR、ネイティブクロックを使用してACLリンクを開始する。<br>
SwitchはACLリンクの開始に伴ってスリープ状態から復帰し、その後は通常のBR/EDR接続手順へ進む。<br>
フェーズ3の受信だけでは復帰処理は完了しない。

## 参考タイミング

次の値は純正コントローラー、互換コントローラーのRFキャプチャから得た参考値となる。

| 項目 | 参考値 |
|---|---:|
| フェーズ1の送信間隔 | 3.75ms |
| フェーズ1の送信開始からフェーズ2応答まで | 1604~2386us |
| フェーズ2の連続応答時間 | 約40ms |
| フェーズ2の応答間隔 | 約320ms |

## 参考コードの実装内容

ESP32のConnectionless Slave Broadcast機能を使用して3フェーズを送受信する。<br>
ESP32のBluetoothコントローラーが適用する白色化は、送受信前に同じ白色化を適用して相殺する方法またはコントローラー側のテストモードによって無効化する。<br>
フェーズ2の17byteはACL受信用コンテキストから取得し、ハードウェアが記録した受信クロックとスロット内時刻をフェーズ3の送信時刻に使用する。<br>
フェーズ2の情報からACLリンクを開始するとSwitchは復帰するが、現在の実装ではSwitchからL2CAPパケットを受信できないため、そのACLリンクを切断して通常のページ接続を開始する。

算出処理は[wakeup_code.c](../src/wake/wakeup_code.c)、ペイロード生成は[wake_payload.c](../src/wake/wake_payload.c)に実装している。
